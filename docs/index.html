L1

Hex to base64

set1::l001
The problem · official

Convert a given hex blob to base64. You are handed 49276d…757368726f6f6d and it must come out as SSdt…c2hyb29t.

The idea

Hex and base64 are two spellings of the same bytes. Decode the hex to raw bytes, then re-encode those very same bytes as base64. No cryptography is involved — the discipline is simply to never "convert hex to base64" directly; the bytes in the middle are the thing.

Core move

hex::from_hex(…) hands you a Vec<u8>; b64::b64_encode(&…) re-spells it. The encodings are transport; the bytes are data.

The code

use crate::util::b64;
use crate::util::hex;

pub fn solve(input_hex: &str) -> Result<String, CpalError> {
    let bytes = hex::from_hex(input_hex)?;
    Ok(b64::b64_encode(&bytes))
}
  • The ? forwards any from_hex failure (odd length or a non-hex digit) up to the caller.
supporting code · util/b64.rs — b64_encode

Three input bytes become one 24-bit number, split into four 6-bit indexes into the alphabet; a short final chunk produces = padding.

pub fn b64_encode(input: &[u8]) -> String {
    let mut out = String::with_capacity((input.len() / 3 + 1) * 4);

    for chunk in input.chunks(3) {
        let b0 = u32::from(chunk[0]);
        let b1 = u32::from(chunk.get(1).copied().unwrap_or(0));
        let b2 = u32::from(chunk.get(2).copied().unwrap_or(0));
        let n = (b0 << 16) | (b1 << 8) | b2;

        let i0 = (n >> 18 & 0x3f) as usize;
        let i1 = (n >> 12 & 0x3f) as usize;
        let i2 = (n >> 6 & 0x3f) as usize;
        let i3 = (n & 0x3f) as usize;

        out.push(ALPHABET[i0] as char);
        out.push(ALPHABET[i1] as char);
        out.push(ALPHABET[i2] as char);
        out.push(ALPHABET[i3] as char);

        if chunk.len() == 1 {
            out.pop(); out.pop(); out.push('='); out.push('=');
        } else if chunk.len() == 2 {
            out.pop(); out.push('=');
        }
    }
    out
}

L2

Fixed XOR

set1::l002
The problem · official

XOR two equal-length buffers, byte for byte. Both are given in hex: 1c01…181c and 6869…7965. Produce the result.

The idea

Decode both to bytes and XOR them positionally: a[i] ^ b[i]. XOR is its own inverse and is commutative, which is exactly why it is the workhorse of ciphers. The result is a Vec<u8>; hex is just how the test prints it.

Core move

One expression: a.iter().zip(b).map(|(&x, &y)| x ^ y). The only failure mode is a length mismatch.

The code

use crate::util::hex;
use crate::util::xor;

pub fn solve(a_hex: &str, b_hex: &str) -> Result<Vec<u8>, CpalError> {
    let a = hex::from_hex(a_hex)?;
    let b = hex::from_hex(b_hex)?;
    xor::xor(&a, &b)
}
supporting code · util/xor.rs — xor 
pub fn xor(a: &[u8], b: &[u8]) -> Result<Vec<u8>, CpalError> {
    if a.len() != b.len() {
        return Err(CpalError::LengthMismatch { a: a.len(), b: b.len() });
    }
    Ok(a.iter().zip(b).map(|(&x, &y)| x ^ y).collect())
}

L3

Single-byte XOR

set1::l003
The problem · official

The message has been XOR'd against a single character. Decrypt it. You'll know you've succeeded when the plaintext reads like meaningful English. The ciphertext is given in hex: 1b37…3736.

The idea

With a single repeated key byte you only have to test 256 candidates. Decrypt against each candidate, score the result for English-likeness, and keep the best. Scoring is util::freq::english_score — a weighted count of lowercase letters and spaces using relative English letter frequencies. Real English is letter-dense, so true plaintext scores far above a wrongly de-keyed (mostly high-bit) buffer. best_single_byte_key runs all 256 and returns the argmax.

Core move

For every k from 0…255 compute score(ct ^ k); the winner is the key. best_single_byte_key hides the loop.

The code

use crate::util::err::CpalError;
use crate::util::freq;
use crate::util::hex;

pub fn solve(cipher_hex: &str) -> Result<(u8, Vec<u8>), CpalError> {
    let ct = hex::from_hex(cipher_hex)?;
    let (key, plain) = freq::best_single_byte_key(&ct);
    Ok((key, plain))
}
  • best_single_byte_key never errors — it always returns the argmax — so the only CpalError path here is the hex decode.
  • key is the byte and plain the decrypted Vec<u8>; the test asserts the exact plaintext.
supporting code · util/freq.rs — english_score + best_single_byte_key 
pub fn english_score(data: &[u8]) -> u32 {
    const FREQ: [u32; 26] = [
        8, 1, 3, 5, 12, 2, 2, 5, 7, 1, 1, 4, 2, 7, 9, 2, 1, 6, 9, 10, 4, 1, 1, 2, 2, 1,
    ];
    let mut total = 0u32;
    for &b in data {
        match b {
            b'a'..=b'z' => total += FREQ[(b - b'a') as usize],
            b' ' => total += 15,
            _ => {}
        }
    }
    total
}

pub fn best_single_byte_key(ciphertext: &[u8]) -> (u8, Vec<u8>) {
    let mut best_key = 0u8;
    let mut best_plain = ciphertext.to_vec();
    let mut best_score = english_score(ciphertext);
    for key in 1..=u8::MAX {
        let plain: Vec<u8> = ciphertext.iter().map(|&b| b ^ key).collect();
        let score = english_score(&plain);
        if score > best_score {
            (best_key, best_plain, best_score) = (key, plain, score);
        }
    }
    (best_key, best_plain)
}

L4

Detect single-byte XOR

set1::l004
The problem · official

Write a function that takes a hex string (with one "single-char-xored" English line buried in it) and detects the line by brute-forcing all 256 characters on every line. There are no obvious boundaries between words, so don't worry about that here.

The idea

Feed the exact L3 attack to every line, keep each line's best-decryption score english_score, and return the argmax line. The planted English line scores far above random noise no matter where it sits — util::freq::best_single_byte_key + english_score (both shown in L3) do the per-line work.

Core move

for (i, line) accumulate (i, key, plain, score); keep the largest score. Exact ties are broken by "first" (later lines only replace on a strict >).

The code

use crate::util::err::CpalError;
use crate::util::freq;
use crate::util::hex;

pub fn solve(lines: &[&str]) -> Result<(usize, u8, Vec<u8>), CpalError> {
    let mut best: Option<(usize, u8, Vec<u8>, u32)> = None;

    for (i, line) in lines.iter().enumerate() {
        let ct = hex::from_hex(line)?;
        let (key, plain) = freq::best_single_byte_key(&ct);
        let score = freq::english_score(&plain);
        if best.as_ref().is_none_or(|b| score > b.3) {
            best = Some((i, key, plain, score));
        }
    }

    match best {
        Some((i, key, plain, _)) => Ok((i, key, plain)),
        None => Err(CpalError::NoLines),
    }
}
  • The four-tuple carries (index, key, plain, score); score is the discriminator and index the answer. |b| score > b.3 reaches the score field.
  • None input is NoLines; an invalid hex digit on any line is surfaced by the hex decode.

Repeating-key XOR

set1::l005
The problem · official

XOR the following plaintext against the repeating key 494345. It's a little long, but I expect you can do it without much trouble:

4275726e696e672027656d2c… ("Burning 'em, if you ain't quick and nimble \n I go crazy when I hear a cymbal")

The idea

L2's XOR is fixed-length; L5 generalizes it: cycle the key back to the start, so byte i of the plaintext meets key byte i % key.len(). This is the repeating-key XOR that L6's ciphertext was made with. The key 494345 decodes to "ICE" — but the code only sees three bytes.

Core move

xor::xore: b ^ key[i % len] for every byte i. One % is the whole trick; an empty key is the only error.

The code

pub fn xore(plain: &[u8], key: &[u8]) -> Result<Vec<u8>, CpalError> {
    if key.is_empty() {
        return Err(CpalError::EmptyKey);
    }
    let len = key.len();
    Ok(plain
        .iter()
        .enumerate()
        .map(|(i, &b)| b ^ key[i % len])
        .collect())
}

L6

Break repeating-key XOR

set1::l006
The problem · official

Base64 the below before you start. Remember that the user's key was a repeating phrase, so if you can't get a reasonable plaintext, try different key lengths in the next step. Decrypt it!

The idea

Two questions: how long is the key? and what is each byte of it?. For the first, note that at the true key length the ciphertext splits into clean "columns" — column c holds plaintext bytes that all met key byte c, so each column is mostly English and has low normalized entropy. At any wrong length the columns interleave several key positions and spread out → higher entropy. key_length searches 2…MAX_KEY_LEN and takes the candidate whose weighted mean column entropy is smallest. Once the length is known, each column is just a single-byte XOR problem, so best_single_byte_key (L3) recovers one key byte at a time.

Core move

(1) minimize mean normalized entropy over column splits to find key_len; (2) per-column best_single_byte_key; (3) xor::xore to decrypt. Entropy is the length discriminator; frequency is the byte discriminator.

The code

use crate::util::b64;
use crate::util::entropy;
use crate::util::err::CpalError;
use crate::util::freq;
use crate::util::xor;

const MAX_KEY_LEN: usize = 48;

pub fn solve(ciphertext: &str) -> Result<(Vec<u8>, Vec<u8>), CpalError> {
    let ct = b64::b64_decode(ciphertext)?;
    if ct.len() < 2 {
        return Err(CpalError::CiphertextTooShort(ct.len()));
    }

    let key_len = key_length(&ct);
    let key: Vec<u8> = (0..key_len)
        .map(|col| {
            let column = column_of(&ct, col, key_len);
            freq::best_single_byte_key(&column).0
        })
        .collect();
    let plaintext =
        xor::xore(&ct, &key).expect("key length is at least two, so the key is non-empty");
    Ok((key, plaintext))
}
  • MAX_KEY_LEN = 48: long enough to exceed this level's key length (29) so the minimum-entropy split is unambiguous; it is also capped at ct.len().
  • The xore is called with .expect — safe because key_length returns ≥ 2, so the key can't be empty. A 1-byte input trips CiphertextTooShort earlier.
supporting code · l006.rs — private key-length helpers 
fn key_length(ct: &[u8]) -> usize {
    let upper = MAX_KEY_LEN.min(ct.len());
    (2..=upper)
        .map(|l| (l, column_entropy(ct, l)))
        .min_by(|a, b| a.1.partial_cmp(&b.1).unwrap_or(std::cmp::Ordering::Equal))
        .map(|(l, _)| l)
        .unwrap_or(2)
}

fn column_entropy(ct: &[u8], l: usize) -> f64 {
    let total = ct.len() as f64;
    (0..l)
        .map(|col| {
            let column = column_of(ct, col, l);
            (column.len() as f64 / total) * entropy::normalized_shannon_entropy(&column)
        })
        .sum()
}

fn column_of(ct: &[u8], col: usize, step: usize) -> Vec<u8> {
    ct.iter().skip(col).step_by(step).copied().collect()
}

column_entropy weights each column by its share of bytes (len/total) so short trailing columns don't dominate — comparing across key lengths means the score must be length-independent.

supporting code · util/entropy.rs — normalized_shannon_entropy

Byte histogram → Shannon entropy, normalized by dividing by log2(256) = 8 so the result is in [0, 1]. 0.0 for a single repeated byte, 1.0 for a perfectly uniform distribution of all 256 values.

pub fn normalized_shannon_entropy(data: &[u8]) -> f64 {
    let n = data.len() as f64;
    if n == 0.0 {
        return 0.0;
    }

    let mut counts = [0usize; 256];
    for &b in data {
        counts[b as usize] += 1;
    }

    let mut h = 0.0;
    for &c in &counts {
        let c = c as f64;
        if c > 0.0 {
            let p = c / n;
            h -= p * p.log2();
        }
    }
    h / 8.0 // log2(256): the maximum entropy a byte value distribution can carry.
}

L7

AES-128 in ECB mode

set1::l007
The problem · official

Decrypt the following base64-encoded file with AES-128 in ECB mode with the key "YELLOW SUBMARINE" (hex: 59454c4c4f57205355424d4152494e45).

The idea

ECB is the block mode that keeps no state: every 16-byte block is encrypted/decrypted independently and in place. So "decrypt the file" is just "decrypt the back-to-back blocks and concat". The aes crate provides AES-128 as a block primitive; this level's solve is only the block-walk and the two preconditions (length is a multiple of 16, and the key is exactly 16 bytes).

Core move

AES is stateless at the block level (that's ECB): chunk the ciphertext into 16-byte blocks, feed each through BlockDecrypt::decrypt_block, and collect. No IV, no chaining, no padding — the payload is already block-aligned.

The code

use aes::cipher::BlockDecrypt;
use aes::cipher::KeyInit;
use aes::Aes128;
use generic_array::GenericArray;

use crate::util::b64;
use crate::util::err::CpalError;

const AES_BLOCK_SIZE: usize = 16;

pub fn solve(encrypted_b64: &str, key: &[u8]) -> Result<Vec<u8>, CpalError> {
    let ct = b64::b64_decode(encrypted_b64)?;
    if ct.len() % AES_BLOCK_SIZE != 0 {
        return Err(CpalError::CiphertextNotBlockAligned(ct.len()));
    }
    if key.len() != AES_BLOCK_SIZE {
        return Err(CpalError::InvalidKeyLength(key.len()));
    }

    let cipher = Aes128::new_from_slice(key).map_err(|_| CpalError::InvalidKeyLength(key.len()))?;

    let mut out = Vec::with_capacity(ct.len());
    for chunk in ct.chunks_exact(AES_BLOCK_SIZE) {
        let mut block = GenericArray::clone_from_slice(chunk);
        cipher.decrypt_block(&mut block);
        out.extend_from_slice(block.as_slice());
    }
    Ok(out)
}
  • Pulled from aes crate + the re-export of its BlockDecrypt trait and generic_array 16-byte wrapper — the only external dependency in this crate.
  • Two explicit preconditions: ciphertext length is a multiple of 16, key is exactly 16 bytes. Both are CpalErrors.

L8

Detect AES in ECB mode

set1::l008
The problem · official

Here's some data at 0x800/546e6b6a6463666d6c626765/08-ecb.txt. Find the lines that contain AES in ECB mode.

The idea

ECB is deterministic and stateless, so an identical 16-byte plaintext block always yields the identical 16-byte ciphertext block. A file of "random-looking" ciphertext under CBC essentially never repeats a block — but an ECB file will, the moment the plaintext has two identical 16-byte spans. So the detector is: for each hex line, split into 16-byte chunks, and flag the line if any chunk appears more than once. A HashSet makes the "has it been seen already?" check O(1).

Core move

for block in ct.chunks_exact(16) → if !seen.insert(block) we already had this block → return its line index. That's it. This is the first place L7's ECB assumption pays off in a detection test.

The code

L9

Implement PKCS#7 padding

set2::l001
The problem · official

Pad any block to a specific block length, by appending the number of bytes of padding to the end of the block. "YELLOW SUBMARINE" padded to 20 bytes becomes "YELLOW SUBMARINE" + "\x04\x04\x04\x04".

The idea

Padding is transport, not cryptography. PKCS#7 fills the final block out to a whole multiple of the block size by appending n identical bytes, each of value n, where n is however many bytes are needed to reach the next block boundary. The subtlety: when the input is already a whole number of blocks, n = block_size, so a full extra block of padding is added — which is exactly what makes unpadding unambiguous. The value 0 can never occur (n ranges 1..=block_size), so the pad count can always be read off the last byte.

Core move

n = block_size - data.len() % block_size — because % binds tighter than -, that is block_size - (len % block_size); when len is already aligned it's a full block_size. Then out.resize(out.len() + n, n as u8) appends n copies of the byte n in one shot.

The code

pub fn pkcs7_pad(data: &[u8], block_size: usize) -> Result<Vec<u8>, CpalError> {
    if !(1..=255).contains(&block_size) {
        return Err(CpalError::InvalidBlockSize(block_size));
    }
    let n = block_size - data.len() % block_size;
    let mut out = data.to_vec();
    out.resize(out.len() + n, n as u8);
    Ok(out)
}

pub fn pkcs7_unpad(data: &[u8], block_size: usize) -> Result<Vec<u8>, CpalError> {
    if !(1..=255).contains(&block_size) {
        return Err(CpalError::InvalidBlockSize(block_size));
    }
    if data.is_empty() || !data.len().is_multiple_of(block_size) {
        return Err(CpalError::BadPadding(data.len()));
    }
    let n = data[data.len() - 1] as usize;
    if n == 0 || n > block_size || !data[data.len() - n..].iter().all(|&b| b as usize == n) {
        return Err(CpalError::BadPadding(data.len()));
    }
    Ok(data[..data.len() - n].to_vec())
}

L10

Implement CBC mode

set2::l002
The problem · official

CBC mode is a block-cipher mode that lets us move irregularly-sized messages even though a block cipher only transforms individual blocks. Each ciphertext block is added to the next plaintext block before the next call to the cipher core; the first plaintext block has no "previous" block, so it is XORed with a fake 0th ciphertext block — the initialization vector (IV). Implement CBC by hand from the AES block function you wrote earlier (run it as decrypt and verify by decrypting what you encrypt), combined with your XOR primitive. Don't cheat — don't use OpenSSL's CBC code. The file here is intelligible when CBC-decrypted against "YELLOW SUBMARINE" with an IV of all \x00.

The idea

A block cipher only knows how to chew a single fixed-size block, so CBC threads the blocks into a chain: before a block is handed to the AES core it is XORed with the previous ciphertext block, and the very first block is XORed with the IV instead — there is no "previous" block yet. That single move is what breaks ECB's property that identical plaintext blocks map to identical ciphertext blocks. Decryption is the mirror image and it is almost as little code as encryption: decrypt each block with the AES core, then XOR the result with the ciphertext block that sits just before it — the only thing that flips is order: the XOR happens after the core call instead of before. So CBC builds straight out of the 16-byte block function from L7 plus XOR.

Core move

decrypt the block with the AES core, then XOR it with the ciphertext block that precedes it (the IV for block 0); push those bytes onto the output and slide the just-consumed ciphertext block in as the new "previous".

pub fn decrypt(ct: &[u8], key: &[u8], iv: &[u8]) -> Result<Vec<u8>, CpalError> {
    if iv.len() != BLOCK {
        return Err(CpalError::InvalidIvLength(iv.len()));
    }
    if key.len() != BLOCK {
        return Err(CpalError::InvalidKeyLength(key.len()));
    }
    if !ct.len().is_multiple_of(BLOCK) {
        return Err(CpalError::CiphertextNotBlockAligned(ct.len()));
    }

    let cipher = Aes128::new_from_slice(key).map_err(|_| CpalError::InvalidKeyLength(key.len()))?;

    let mut out = Vec::with_capacity(ct.len());
    let mut prev = <[u8; BLOCK]>::try_from(iv).expect("iv is exactly 16 bytes");
    for block in ct.chunks_exact(BLOCK) {
        let mut buf = GenericArray::<u8, _>::clone_from_slice(block);
        cipher.decrypt_block(&mut buf);
        for (i, &b) in buf.iter().enumerate() {
            out.push(b ^ prev[i]);
        }
        prev = <[u8; BLOCK]>::try_from(block).expect("each chunk is exactly 16 bytes");
    }
    Ok(out)
}

An ECB/CBC detection oracle

set2::l003
The problem · official

Now that you have ECB and CBC working: write a function that generates a random AES key (16 random bytes) and a function that encrypts data under a random key. Look like encryption_oracle(input) → [jibber jabber]. Under the hood, append 5–10 random bytes (count chosen at random) before the plaintext and 5–10 after it, then choose to encrypt under ECB 1/2 the time and under CBC the other half (random IVs for CBC). Detect the block-cipher mode the function is using each time — code that, pointed at a box that might be running ECB or CBC, tells you which one it is.

The idea

ECB is stateless and deterministic, so two identical 16-byte plaintext blocks always yield two identical 16-byte ciphertext blocks (the leak you exploited back in L8). CBC's fresh IV and per-block chaining mean that essentially never happens. So the whole detector is: does the ciphertext carry a repeated 16-byte block? The only design question is how to get the repeat to show up under the oracle's random prefix, which shifts where each block boundary lands. The answer: feed the box a message with a long run of identical plaintext — 256 copies of 'A' — so that no matter where the prefix drops, at least two whole 16-byte blocks are pure 'A', land on a 16-byte boundary, and line up with each other. Under ECB they encrypt to the same block (the signature appears); under CBC they do not.

Core move

walk the ciphertext in 16-byte strides, put each block in a HashSet, and the first repeated block is ECB; if none repeats it's CBC.

The code

L12

Byte-at-a-time ECB decryption

set2::l004
The problem · official

Copy your oracle to a new function that encrypts buffers under ECB mode using a consistent but unknown key (a single key, assigned once, never revealed). Have it append, before encrypting, the secret below — base64-decode it in code, not by hand, so its contents stay unknown. What you now have is AES-128-ECB(your-string || unknown-string, random-key). It turns out: you can decrypt that unknown-string with repeated calls to the oracle. Discover the block size, detect that it is ECB, then — knowing the block size — line each next unknown byte up as the last byte of a block, build a dictionary of every possible last byte, match, and repeat for the next byte. This is the first challenge whose solution breaks real crypto: ECB looks like penguins through glass, and now you can read the penguins.

The idea

ECB is per-block and deterministic, so two identical 16-byte plaintext blocks always yield two identical ciphertext blocks — the leak L8 exposed and L11 learned to detect. Here there is no random prefix to fight and no mode to detect (the box is locked to ECB under a fixed key); the only enemy is a secret the box silently tacks on the end of everything you send. The whole attack is alignment. For the byte at position k you already control, or have recovered, the fifteen plain bytes immediately before it. Pad them out to a full block so the unknown byte k lands exactly on that block's final position, ask the oracle what ciphertext block that produces, and — since you don't yet know that last byte — probe it: re-run the oracle on that known-15 block plus each of the 256 possible last bytes and keep the one whose first block matches. Do that for k = 0, then 1, then 2, … and the unknown string decodes itself, byte by byte.

Core move

line the next unknown byte up as the final byte of a 16-byte block whose other fifteen bytes you already know (controlled filler for the first block, earlier recovered bytes thereafter), then brute-force that byte across 0–255 by re-invoking the oracle; whichever candidate reproduces the observed block is the byte. Slide the window forward one byte and the whole unknown string falls out.

The code

pub fn solve() -> Vec<u8> {
    recover(unknown_len(), &|input| oracle(input))
}
  • oracle is the black box: append the unknown string, PKCS#7-pad to 16, encrypt under the fixed ECB KEY, and return only ciphertext. solve is a two-line driver — discover how many bytes the box appends (unknown_len), then read them off one at a time (recover) — and is the headline answer.
  • No new CpalError variant is needed: the attack is deterministic — for the final byte of a block, exactly one of the 256 candidates reproduces the observed block — so every slice is proven in-bounds and the probe loop is guaranteed to hit its break.
  • KEY is a fixed 16-byte value only so the result is reproducible; it is never exposed or read back, the same "draw the key, then stop using it" move as L11.
  • Everything reuses existing util/ primitives — b64::b64_decode (L1), pad::pkcs7_pad (L9), and aes::ecb_encrypt (L11) — so L12 adds no new module and no new dependency.

fn recover(total: usize, enc: &dyn Fn(&[u8]) -> Vec<u8>) -> Vec<u8> {
    let mut recovered = Vec::with_capacity(total);
    for k in 0..total {
        let mut known15 = if k < BLOCK {
            vec![FILLER; BLOCK - 1 - k]
        } else {
            Vec::with_capacity(BLOCK - 1)
        };
        if k < BLOCK {
            known15.extend_from_slice(&recovered[..k]);
        } else {
            known15.extend_from_slice(&recovered[k - (BLOCK - 1)..k]);
        }
        let left = BLOCK - 1 - k % BLOCK;
        let block = (left + k) / BLOCK;
        let observed = enc(&vec![FILLER; left]);
        let observed_block = &observed[block * BLOCK..block * BLOCK + BLOCK];

        let mut cand = known15;
        cand.push(0);
        for c in 0..=u8::MAX {
            cand[BLOCK - 1] = c;
            if enc(&cand)[..BLOCK] == *observed_block {
                recovered.push(c);
                break;
            }
        }
    }
    recovered
}

L13

ECB cut-and-paste

set2::l005
The problem · official

Your system turns user input into a string of the form email=email&uid=id&role=user_type, PKCS#7-pads it, AES-128-ECB-encrypts it, and gives the result to you. The user can read their own ciphertext, and the system later decrypts it to check permissions. Your task: using the string foo, produce an input_with_id that will result in a cookie that, when decrypted, parses as role=admin.

The idea

This is the ECB lesson of L8 in the wild. ECB is per-block and deterministic, so a cookie is just a bag of interchangeable 16-byte blocks — you can reorder, copy, or substitute them freely and each still decrypts to the same bytes. The trick is to put admin where it must land, right after role=. The way to do that is to exploit the padding: pick an email whose bytes, together with the fixed &uid=10&role=user suffix, line admin up in its own fresh 16-byte block, followed by exactly eleven 0x0B bytes. When that block is pasted last, those eleven bytes read as perfectly valid PKCS#7 padding and vanish on un-pad, leaving a clean role=admin. No key is needed — only the encrypting oracle (turn an email into a cookie) and the authenticating oracle (check a cookie for role=admin).

Core move

craft an email that carries admin in its own PKCS#7-padded block, encrypt it, and splice the honest cookie into block0 + block2 + block1 so that the pasted block lands after role=; its trailing eleven 0x0B bytes are stripped as padding on the way back in.

The code

pub fn solve() -> Vec<u8> {

    // then the `admin` block last — its eleven 0x0B bytes read as PKCS#7 padding.
    let mut forged = Vec::with_capacity(3 * BLOCK);
    forged.extend_from_slice(&cookie[0..BLOCK]);
    forged.extend_from_slice(&cookie[2 * BLOCK..3 * BLOCK]);
    forged.extend_from_slice(&cookie[BLOCK..2 * BLOCK]);

    auth(&forged).expect("the forged cookie authenticates as role=admin");
    forged
}

  • The cut-and-paste property is pinned directly by a test: block 1 of the forged cookie is a byte-for-byte copy of block 1 of the honest cookie for the same email. No block was ever generated without the oracle.
  • The pasted block admin\x0b×11 un-pads on its own (eleven valid pad bytes), so the spliced plaintext is exactly email=…&uid=10&role=admin — which is why auth accepts it.
  • The two oracles are the whole interface: encrypt_profile (L11's ecb_encrypt) and auth (L7/L10's ecb_decrypt + un-pad). A new CpalError::AuthFailed variant names the "you are not admin" outcome.

Byte-at-a-time ECB decryption (harder)

set2::l006
The problem · official

Same setup as L12 — a box that returns AES-128-ECB(unknown-string, random-key) for a consistent-but-unknown key, appending the same base64 secret from L12 and taking your input — except now it prepends a random amount of random bytes to every plaintext before encrypting. Decryption is a lot harder. It's still AES-128-ECB(random-bytes || your-string || unknown-string, random-key). You can recover it, though: with a random prefix, you first need to determine how many bytes it is. Once you've done that, byte-at-a-time ECB decryption is trivial.

The idea

L12's only enemy was a secret the box tacked on the end; here a second enemy sits up front — a random prefix whose length the caller can't see. That matters because L12's alignment counted filler from the very front of the plaintext, and a random prefix of length P off-block shifts where every boundary falls. So the attack splits into two moves. First, measure P: ciphertext length is always (P + input + n) rounded up to a multiple of 16, where n is the secret's length. Probing 0..=16 input lengths walks every residue mod 16, so the minimum of ct.len() - input.len() is P + n + 1 — and the attacker already knows n (the blob was handed to it, so it decodes it and reads its length), leaving P = that minimum − 1 − n. Second, run L12's byte-at-a-time core past the prefix: for the byte at position k, the fifteen known plain bytes before it are controlled filler plus already-recovered bytes (FILLER^(15−m) ++ recovered[k−m..k], m = min(k,15)), and the filler length is chosen not merely to align that byte on a block's final position (P + left + k) ≡ 15 mod 16 but to be long enough that those fifteen bytes stay inside attacker-controlled territory, never the unknown prefix. Read that block off the observed ciphertext, probe it against all 256 candidates, keep the match, and slide forward exactly as in L12.

Core move

discover the random prefix's length from the length staircase (min(ct.len() − input.len()) − 1 − n), then run L12's byte-at-a-time attack with filler that both aligns byte k to a block boundary and is long enough that the fifteen known bytes before it never touch the prefix.

The code

pub fn oracle(input: &[u8]) -> Vec<u8> {

fn prefix_len(unknown: &usize) -> usize {
    let total = (0..=BLOCK)
        .map(|len| oracle(&vec![FILLER; len]).len() - len)
        .min()
        .expect("at least one sample")
        - 1;
    total - unknown
}

fn recover(total: usize, prefix_len: usize, enc: &dyn Fn(&[u8]) -> Vec<u8>) -> Vec<u8> {
    let mut recovered = Vec::with_capacity(total);
    for k in 0..total {
        let m = k.min(BLOCK - 1);
        let mut known15 = vec![FILLER; BLOCK - 1 - m];
        known15.extend_from_slice(&recovered[k - m..k]);

        let min_left = if k < BLOCK { BLOCK - 1 - k } else { 0 };
        let mut left = 0;
        while (prefix_len + left + k) % BLOCK != BLOCK - 1 {
            left += 1;
        }
        if left < min_left {
            left += BLOCK;
        }

        let block = (prefix_len + left + k) / BLOCK;
        let observed = enc(&vec![FILLER; left]);
        let observed_block = &observed[block * BLOCK..block * BLOCK + BLOCK];

        let probe_left = left + k - (BLOCK - 1);
        let mut cand = vec![FILLER; probe_left];
        cand.extend_from_slice(&known15);
        cand.push(0);
        let last = cand.len() - 1;
        for c in 0..=u8::MAX {
            cand[last] = c;
            let probe = &enc(&cand)[block * BLOCK..block * BLOCK + BLOCK];
            if probe == observed_block {
                recovered.push(c);
                break;
            }
        }
    }
    recovered
}

L15

Validate PKCS#7 padding

set2::l007
The problem

In the previous level we built a PKCS#7 pad/unpad pair. Now nail the rule down: write a validator that takes a buffer and a block size and tells you whether it is correctly padded. At the 16-byte AES block, "ICE ICE BABY" + 04 04 04 04 is, while "ICE ICE BABY" + 05 05 05 05 and "ICE ICE BABY" + 01 02 03 04 are not.

The idea

A buffer is legal PKCS#7 exactly when its final byte n is in 1..=block and its last n bytes are all n. Nothing else counts. "ICE ICE BABY" is twelve bytes, so four 0x04 pad it to a clean sixteen (12 + 4 = 16). A trailing 0x05, though, claims five pad bytes on a twelve-byte body — only four trail it, and five would overrun the block. And 01 02 03 04 fails even before the count: the pad bytes are not all equal. solve is a deliberately thin wrapper that pins the 16-byte block and forwards the verdict to util::pad.

Core move

Validation is its own discipline, not a decrypt: read the last byte, check that it is in range, then require that many trailing bytes to all match it. The boundary between "valid" and "malformed" is exactly the one bit a Set 3 padding oracle will later leak — so getting this rule airtight is the whole point.

The code

pub fn pkcs7_unpad(data: &[u8], block_size: usize) -> Result<Vec<u8>, CpalError> {

}

L16

Exploit mispadding (bit flip)

set2::l008
The problem

A service encrypts a fixed comment value plus your input in CBC mode under a hidden key, then will decrypt-and-check any ciphertext you hand it for the substring admin=true. Your input is passed through a sanitizer that rejects the literal marker, and it is sandwiched between two fixed, public delimiters. Get the service to decrypt a crafted block into a profile that contains admin=true.

The idea

The sanitizer stops you typing the marker, but it cannot stop you choosing which bytes a block decrypts to. CBC decodes block i as P_i = D(C_i) XOR C_{i-1}; the block in front of it is not a guard, it is a knob. Flip a bit in C_{i-1} and you flip that very bit in P_i, leaving every other block untouched. The public prefix (two whole blocks) plus your four-byte input plus the public suffix line up so that one entire data block is fully known to you — pick the input to be the four bytes that make that block's target value exactly input ++ ";admin=true;", then XOR a hand-computed mask into the predecessor block so it decodes to that. The rest of the profile stays pristine and still un-pads.

Core move

You never learn the key. You pick which bits in one ciphertext block to flip so the next block decodes to whatever you wrote. The public delimiters do the alignment work that makes a whole block attacker-known — and they line up with the pad rule L15 just nailed down.

The code

pub fn forge() -> Vec<u8> {

    target[..input.len()].copy_from_slice(input.as_bytes());

}

    is_admin(&forge())

L17

The CBC padding oracle

set3::l001
The problem

The service you attack turns encrypted session cookies into plaintext behind the scenes, and distinguishes "padding was valid" from "padding was not" in its response. It happily decrypts any ciphertext you submit and tells you just that one bit. Armed with nothing but the oracle and each cookie's public IV, read the plaintext off — without the key.

The idea

You can break CBC whenever a padding check leaks. CBC decodes block i as P_i = D(C_i) XOR C_{i-1}. You don't control C_i — you control the block slid in front of it. Submit the tampered pair [B_i, C_i]; the oracle runs padding on the first block, which decodes to D(C_i) XOR B_i. Since D(C_i) is fixed and unknown, that checked value is a constant XORed with sixteen bytes you choose. Force every byte after position j of B_i to make the tail read as a known p = 16 − j-byte pad, then sweep B_i[j] over all 256 values until the oracle goes green — that one value is D(C_i)[j]. Walk j back from 15 to 0 and you hold the whole raw block D(C_i); the real plaintext block is just D(C_i) XOR C_{i-1} (the IV for the first).

Core move

The oracle tells you about padding, not the key — but that one distinguishing bit, driven across sixteen bytes × up to 256 probes, peels D(C_i) off block by block. This is the most-deployed-in-the-wild attack in the set, and it runs on the very pad boundary L15 nailed down.

The code

pub fn solve(
    ct: &[u8],
    iv: [u8; BLOCK],
    oracle: &dyn Fn(&[u8]) -> bool,
) -> Result<Vec<u8>, CpalError> {
    if ct.is_empty() || !ct.len().is_multiple_of(BLOCK) {
        return Err(CpalError::CiphertextNotBlockAligned(ct.len()));
    }

    let blocks: Vec<[u8; BLOCK]> = ct.chunks_exact(BLOCK)
        .map(|b| b.try_into().expect("chunk is exactly 16 bytes"))
        .collect();

    let mut out = Vec::with_capacity(ct.len());
    for (i, block) in blocks.iter().enumerate() {
        let raw = recover_raw(block, oracle);            // = D(C_i)
        let prev: &[u8] = if i == 0 { &iv } else { &blocks[i - 1] };
        for k in 0..BLOCK {
            out.push(raw[k] ^ prev[k]);                  // P_i = D(C_i) XOR C_{i-1}
        }
    }

    pad::pkcs7_unpad(&out, BLOCK)
}

  • The recovered per-block value is the raw D(C_i); only the final XOR against the predecessor (or IV) yields the plaintext, and stripping the trailing pad block leaves the body. fn recover_raw(target: &[u8], oracle: &dyn Fn(&[u8]) -> bool) -> [u8; BLOCK] {
    let mut raw = [0u8; BLOCK];
    for j in (0..BLOCK).rev() {
        let pad_value = (BLOCK - j) as u8;

        let mut b = [0u8; BLOCK];
        for i in (j + 1)..BLOCK {
            b[i] = raw[i] ^ pad_value; // force every later byte to pad_value
        }
        for c in 0..=u8::MAX {
            b[j] = c ^ pad_value;
            let mut probe = [0u8; 2 * BLOCK];
            probe[..BLOCK].copy_from_slice(&b);
            probe[BLOCK..].copy_from_slice(target);
            if oracle(&probe) {
                raw[j] = c; // checked block j decrypts to pad_value only when raw[j] == c
                break;
            }
        }
    }
    raw
}

L18

Implement CTR, the stream cipher mode

set3::l002
The problem

Decrypt the blob at the top in CTR mode. CTR turns the AES block cipher into a stream cipher: instead of encrypting the plaintext, it encrypts a running 16-byte counter and XORs the resulting keystream against the data, and decrypting is the identical operation again. Base64 is only a transport — this is the cipher. The challenge fixes the parameters: key YELLOW SUBMARINE, nonce 0, and a 16-byte counter built from an 8-byte nonce followed by an 8-byte little-endian block count.

The idea

CBC chained each block to the previous ciphertext. CTR drops that feedback entirely and instead encodes a single monotone counter: the counter is fed through the AES block core, its 16-byte output is XORed against the next 16 bytes of the stream, and the counter rolls one for each block. Because the keystream depends on the key and the counter alone — not on the data — XOR is self-inverse and the same function that encrypts also decrypts. No chaining, no padding; when the stream ends mid-block, the last partial chunk just gets that many keystream bytes and stops.

Core move

The counter is the only moving part: 8 fixed nonce bytes and a 8-byte little-endian block index starting at 0. Increment the index, encrypt its block under the key, XOR. Encrypt and decrypt are the identical function — the whole point of a stream cipher.

The code

The level is thin glue; the reusable keystream lives in util::ctr:

pub fn ctr(stream: &[u8], key: &[u8], nonce: u64) -> Result<Vec<u8>, CpalError> {
    if key.len() != BLOCK {
        return Err(CpalError::InvalidKeyLength(key.len()));
    }
    let cipher = Aes128::new_from_slice(key).map_err(|_| CpalError::InvalidKeyLength(key.len()))?;
    let prefix = nonce.to_le_bytes();

    let mut out = Vec::with_capacity(stream.len());
    for (i, chunk) in stream.chunks(BLOCK).enumerate() {
        let mut counter = [0u8; BLOCK];
        counter[..8].copy_from_slice(&prefix);
        counter[8..].copy_from_slice(&(i as u64).to_le_bytes());

        let mut keystream = GenericArray::clone_from_slice(&counter);
        cipher.encrypt_block(&mut keystream);
        for (j, &b) in chunk.iter().enumerate() {
            out.push(b ^ keystream[j]);
        }
    }
    Ok(out)
}

  • CTR is involutive — ctr(ctr(x, k, n), k, n) == x. There is no unpadding step, because there was never any padding: the stream simply stops when the stream ends, and the last partial block is XORed against just as many keystream bytes.
  • It reuses the same AES-128 block core that util/aes and util/cbc already wrap (Aes128::encrypt_block). The only new idea is XORing a counter instead of chaining ciphertext. No new CpalError variant — the only failure mode ctr can raise is a bad key length.
  • The test asserts a printable-ASCII proportion and a short head rather than pinning the whole decrypted string, because the level demonstrates the mode, not the message: a structural property proves the stream decoded correctly without hardcoding a large expected blob. An all-zero 16-byte stream under nonce 0 is cross-checked against plain ecb_encrypt of the same sixteen zero bytes, verifying the counter layout without duplicating the AES work.

L19

Break fixed-nonce CTR mode using substitutions

set3::l003
The problem

Take CTR and fix its nonce to 0, resetting the counter to zero before every message, and use it to encrypt several short messages. Because every message is XORed against the same leading keystream, the ciphertexts leak each other: recover the plaintext of all forty of them. The plaintext is W. B. Yeats's public-domain poem "Easter, 1916."

The idea

L18 showed that a CTR keystream depends on the key and the counter alone, never on the data. Fix the nonce and restart the counter for each message, and you have run the very same keystream prefix over every line. Two consequences fall out of a single XOR:

  • XOR two ciphertexts. ca ⊕ cb = (pa ⊕ k) ⊕ (pb ⊕ k) = pa ⊕ pb. The shared stream cancels, leaving the two plaintexts' XOR — useful even without knowing any plaintext at all.
  • One known pair pins the stream. cx ⊕ px = k, the shared keystream itself. XOR that back into every other ciphertext and, up to the known line's length, each target's bytes read off as plaintext. A known line at least as long as the longest target (line 38, 38 bytes here) recovers all of them; a shorter one recovers only the shared prefix, and the rest stays ciphertext.
Core move

Recover the keystream by XORing a known ciphertext against its plaintext. Apply that keystream to every other ciphertext and the whole range of lines is undone from a single substitution. The failure mode — a fixed, repeating nonce — is exactly the stream-cipher's only weakness.

                .map(|(i, &b)| match ks.get(i) {
                    Some(&k) => b ^ k,  // keystream still active: decode to plaintext
                    None => b,          // past the keystream: leave the ciphertext as-is
                })
                .collect()
        })
        .collect()
}

Detect block cipher mode

set3::l004
The problem

Here are eighty 64-byte AES-128 ciphertexts, base64, each encrypted under a fresh random key you will never see. Half were made in ECB and half in CBC, interleaved. There is no key to recover and no oracle to query — you can only look. For every line, decide which mode produced it.

The idea

The one difference that surfaces in the ciphertext itself, without a key, is whether blocks repeat. ECB is a stateless, deterministic function of each block: two identical 16-byte plaintext blocks become two identical 16-byte ciphertext blocks. CBC chains every block through the previous ciphertext and a fresh random IV, so two identical plaintext blocks land in two different ciphertext blocks. So the test is a single scan: does any 16-byte block appear twice? A repeat means ECB; no repeat means CBC. It is the very rule L8 and L11 already rely on, this time applied to a stored batch instead of a live oracle.

Core move

Look for the repeated 16-byte block. Repeat ⇒ ECB, no repeat ⇒ CBC. No key, no oracle — the mode is written into the ciphertext blocks themselves, because only the deterministic mode preserves block equalities.

The code

The entire answer is a five-line scan plus a map of it over the batch. The detector is re-implemented here (rather than imported from L11) so the set3 module stays decoupled, and the batch is minted in the crate the way L19 mints its lines:

pub fn classify(ct: &[u8]) -> BlockMode {

            return true;   // a 16-byte block already seen → deterministic mode
        }
    }
    false
}

}

Mersenne Twister RNG

set3::l005
The problem

Most languages' rand() is the Mersenne Twister, and the challenge is to hand-roll the machine instead of calling the library: implement MT19937 from the C reference form, seed it with 5489, and print the first 32 32-bit words. The expected list is pinned on the challenge page, so a correct implementation matches it word for word.

The idea

The whole machine is one 624-word u32 array. A single 32-bit seed stretches across it: s[0] = seed and s[i] = 1812433253 · (s[i−1] ⊕ s[i−1] >> 30) + i (mod 2^32). Producing a word is two steps. When the state is exhausted it is twisted: each word becomes s[k+397] ^ (y >> 1) ^ (low bit of y ? 0x9908B0DF : 0), where y is the top bit of s[k] or the low 31 bits of s[k+1]. The drawn word is then tempered with four XOR-shift passes that spread the low-bit correlation of the raw state word across all 32 bits. 624 words of 32 bits is 19968 bits, just past 19937: that is what makes the period 2^19937 − 1, the Mersenne prime the family is named for. One subtlety the reference values hinge on: the canonical form, the one std::mt19937 runs, starts the draw index at 624, so the very first draw twists before it produces a word.

Core move

Get the twist right: the k+397 lag, the low bit that selects MATRIX_A, and the twist-before-first-draw convention. Every reference is the same machine (the C source, std::mt19937, Python's random), so a correct implementation agrees with all of them on every word, and the KATs pin the stream head, seed 0, and a triple that straddles the twist boundary.

The code

The machine is two small loops: a seed-stretch that fills the state, and the twist that runs when the 624 words are exhausted. The constants doing the work: N = 624, M = 397, UPPER = 0x8000_0000, LOWER = 0x7FFF_FFFF, MATRIX_A = 0x9908_B0DF, SEED_MUL = 1_812_433_253:

pub fn new(seed: u32) -> Self {
    let mut state = [0u32; N];
    state[0] = seed;
    for i in 1..N {
        state[i] = SEED_MUL
            .wrapping_mul(state[i - 1] ^ (state[i - 1] >> 30))
            .wrapping_add(i as u32);
    }
    Self { state, idx: N }   // index 624: the first draw twists
}
pub fn next_u32(&mut self) -> u32 {
    if self.idx >= N {
        for k in 0..N {
            let y = (self.state[k] & UPPER) | (self.state[(k + 1) % N] & LOWER);
            self.state[k] = self.state[(k + M) % N]
                ^ (y >> 1)
                ^ if y & 1 != 0 { MATRIX_A } else { 0 };
        }
        self.idx = 0;
    }
    let word = self.state[self.idx];
    self.idx += 1;
    temper(word)
}

fn temper(mut word: u32) -> u32 {
    word ^= word >> 11;
    word ^= (word << 7) & 0x9D2C5680;
    word ^= (word << 15) & 0xEFC60000;
    word ^= word >> 18;
    word
}
  • The twist is a single forward in-place loop: each state[k] is written from state[(k + M) % N] plus a mix of the two words ahead, which is safe because the twist always reads ahead of where it writes. The two-loop form in the C reference is the same computation split to avoid the modulo.
  • next_u32 is the only drawing method besides new: the state and index are private, so the module cannot leak an untempered word. The follow-ups that need the raw state get it just-in-time, as L23's from_outputs adds.
  • No new CpalError variant, no data file: the RNG is generated in the crate, and solve returns the raw Vec<u32> stream, no Result.

Crack an MT19937 seed

set3::l006
The problem · official

Make sure your MT19937 accepts an integer seed. Write a routine that performs the following operation: wait a random number of seconds between, I don't know, 40 and 1000; seed the RNG with the current Unix timestamp; wait a random number of seconds again; return the first 32-bit output of the RNG. From that 32-bit output, discover the seed.

The idea

A timestamp-seeded RNG is a clock, not a source of entropy. The seed space is not 2^32; it is a few thousand Unix seconds, because the server's wait is bounded. An attacker who sees one 32-bit word and knows the observation time to within that window has only about 1000 candidates. Each candidate is one seed-stretch of the 624-word state, one twist, one temper, one comparison: a full window is a few thousand word operations, under a millisecond. The brute force is a loop, not a cryptographic attack on the algorithm. And the moment one output word matches, the seed is known, and the entire future stream is just next_u32 called again. The machine is the one from L21; this level is the observation side: walk the time window backward and find the seed whose first draw is the word you saw.

Core move

Search backward from the observation time, not forward from the epoch: for back in 0..=1000 { seed = current.wrapping_sub(back) }. The newest candidate is the most plausible seed, so the first match is the deterministic, testable behavior. When no candidate in the window produces the observed word, the result is a new just-in-time CpalError::NoSeedFound variant.

The code

One loop over the window; each candidate seeds the machine from L21 and draws exactly one word. The window is a constant: 1000 s covers the challenge's upper bound on the wait.

pub fn solve(current_unix_time: u32, first_output: u32) -> Result<u32, CpalError> {
    (0..=WINDOW)
        .map(|back| current_unix_time.wrapping_sub(back))
        .find(|&seed| Mt19937::new(seed).next_u32() == first_output)
        .ok_or(CpalError::NoSeedFound)
}
  • wrapping_sub keeps the loop total when the observation time is under 1000: the low candidates wrap to the far future and simply never match, so the semantics stay "search the last 1000 timestamps".
  • Each trial is one seed-stretch, one twist, one temper, so a full 1000-candidate window costs roughly a thousand word operations, no optimization needed.
  • The NoSeedFound variant in util/err.rs is the just-in-time error addition this level needed; its not-found test uses a window verified collision-free against the C oracle.
  • Two properties pin the same contract over the whole domain the window can reach: any seed inside the window is recovered, and a seed outside it is NoSeedFound. MT19937's first draw is not injective, so both stay inside a seed range verified collision-free.

Worked example

Clone an MT19937 RNG from its output

set3::l007
The problem · official

The internal state of MT19937 consists of 624 32-bit integers; each output is a tempered state word, not the raw word. The temper is invertible, so one full batch of 624 consecutive outputs that begins at a twist boundary is exactly enough to reconstruct the whole state: untemper each output back into its state word, splice the 624 words into a fresh generator, and the clone is bit-for-bit the original, producing every word the original would have produced from that point on. Then, tap it and predict the next output.

The idea

L22 cracked the seed by brute-forcing a tiny time window. This level is the other side of the same machine: you never need the seed, you only need one full pass of outputs. Each of the 624 outputs is the raw state word run through the four-pass temper of L21; the temper only permutes the bits of that word, so it is reversible. Undo the four passes in reverse order and each output gives back its exact state word. One complete 624-word pass, untempered, is the generator's full state, and the whole attack is one untemper per word plus a splice. The machine that makes this work is a pair of functions added just-in-time to util/mt19937: untemper inverts the temper on one word, and from_outputs runs the 624 and splices the result into a fresh Mt19937.

Core move

Inverting a masked left shift is not one step. The temper's >> 18 inverts with a single >> 18 (36 exceeds the word), its << 15 & mask inverts with one reapplication, its >> 11 cascades a second >> 22 step, but its << 7 & mask is an order-8 permutation, so the inverse is seven more applications. Get the cascade right and one pass of outputs reconstructs the whole state.

The code

Two new functions sit in util/mt19937.rs; the level's solve is the one-line splice.

pub fn untemper(mut word: u32) -> u32 {
    word ^= word >> 18;
    word ^= (word << 15) & 0xEFC60000;
    for _ in 0..7 {
        word ^= (word << 7) & 0x9D2C5680;
    }
    word ^= word >> 11;
    word ^= word >> 22;
    word
}

pub fn from_outputs(outputs: &[u32; 624]) -> Self {
    let mut state = [0u32; N];
    for i in 0..N {
        state[i] = untemper(outputs[i]);
    }
    Self { state, idx: N }   // next draw twists, exactly like the original
}
pub fn solve(outputs: &[u32; 624]) -> Mt19937 {
    Mt19937::from_outputs(outputs)
}
  • from_outputs positions the spliced generator at idx = N, so its first draw twists the reconstructed state, exactly as the original does at the same point: the clone and the original stay in lockstep from the splice onward.
  • The batch must be one complete pass, 624 draws beginning at a twist boundary. A partial or misaligned batch untempers into the wrong state, and the clone diverges on the very next draw.
  • No new CpalError variant, no data file: the attack is pure word arithmetic, and solve hands back the live generator so the caller can keep tapping it, no Result.

Create an MT19937 stream cipher and break it

set3::l008
The problem · official

Any PRNG makes a trivial stream cipher: generate 8-bit outputs, call them the keystream, and XOR the plaintext against them. Do it with MT19937 and a 16-bit seed, and verify that encrypting and decrypting both work. Then use it to encrypt a known plaintext, fourteen consecutive A characters behind a random prefix of random characters, and recover the 16-bit seed from the ciphertext. The same idea mints a "password reset token" from the current time, and the check is whether a given token could actually be the output of a time-seeded MT19937.

The idea

The cipher is the easy half: the words of L21 are four keystream bytes each, low byte first, and the cipher is one XOR, so it is its own inverse, the same shape as the CTR code of L18. The break is the seed, not the machine. A 16-bit seed is 65536 candidates, and the known tail pins the check: the attacker saw the whole ciphertext and knows the plaintext ends in fourteen A bytes, so they decrypt the ciphertext with each candidate seed and keep the one whose plaintext still ends in that tail. A wrong seed XORs two different keystreams into the last fourteen positions and reads as random noise, so exactly one candidate matches, and the ascending scan makes the answer deterministic. The "password reset token" half is just L22's window attack with a smaller candidate set: a token seeded from the current time only ever took one of a few thousand seeds.

Core move

Recovery is not a cryptanalysis of MT19937, it is a size argument: 2^16 candidates against a 14-byte check. One encrypt call per candidate, one ends_with check, and the seed is the only candidate that survives. No untempering, no state splicing: the known tail does the whole job.

The code

The level module is two functions; the machine they build on is util/mt19937.

pub fn encrypt(plain: &[u8], seed: u16) -> Vec<u8> {
    let mut rng = Mt19937::new(seed as u32);
    let mut out = Vec::with_capacity(plain.len());
    let mut word = 0u32;
    let mut byte_in_word = 4u32; // force a fresh word before the first byte
    for &b in plain {
        if byte_in_word == 4 {
            word = rng.next_u32();
            byte_in_word = 0;
        }
        out.push(b ^ ((word >> (8 * byte_in_word)) as u8));
        byte_in_word += 1;
    }
    out
}
pub fn solve(ciphertext: &[u8], known_tail: &[u8]) -> Result<u16, CpalError> {
    if ciphertext.len() < known_tail.len() {
        return Err(CpalError::CiphertextTooShort(ciphertext.len()));
    }
    for seed in 0..=u16::MAX {
        if encrypt(ciphertext, seed).ends_with(known_tail) {
            return Ok(seed);
        }
    }
    Err(CpalError::NoSeedFound)
}
  • The keystream is four bytes per word, low byte first: the first stream byte is the low byte of the first tempered word. Encrypting sixteen zero bytes gives the raw keystream, and the tests pin its head for seeds 0 and 1 against the locked L21 vectors.
  • No new CpalError variant: a too-short ciphertext reuses CiphertextTooShort, and an unmatchable tail reuses NoSeedFound.
  • encrypt is the decrypt: XOR is its own inverse, so the cipher and its break share one function, the way the CTR level's ctr does.

Break "random access read/write" AES CTR

set4::l001
The problem · official

Back to CTR. Encrypt the recovered plaintext from L12 (the ECB exercise) under CTR with a random key that is unknown to you, but that you hold on to. Now, write the code that lets you "seek" into the ciphertext, decrypt, and re-encrypt with different plaintext. Expose this as a function, like, edit(ciphertext, key, offset, newtext). Imagine the "edit" function was exposed to attackers by means of an API call that did not reveal the key or the original plaintext; the attacker has the ciphertext and controls the offset and the "new text". Recover the original plaintext.

The idea

The seek is the trap. The CTR keystream is a pure function of the key and the counter (L18's layout: 8-byte nonce, 8-byte little-endian block count), so byte N of the stream can be generated without walking from the start. Every call to edit produces the same keystream, and a single full-length zero edit at offset 0 hands the caller the raw stream: 0 ^ KS = KS. The attacker already holds C = P ^ KS, so one byte-wise XOR gives P, the entire original plaintext, in a single oracle call, with the key never in sight. The challenge's food-for-thought variant is the same hole dressed up for disk encryption: a "seek" that can overwrite arbitrary plaintext at arbitrary positions is a keystream-leak machine.

Core move

One full-length zero edit leaks the entire keystream, and C ^ KS = P reads the plaintext back in its entirety. One oracle call, key never in sight: the "random access read/write" primitive is the attack surface, not the cipher.

The code

The level module is two functions; the keystream they build on is util/ctr.

pub fn edit(ct: &[u8], key: &[u8], offset: usize, newtext: &[u8]) -> Result<Vec<u8>, CpalError> {
    let plain = ctr::ctr(ct, key, NONCE)?;

    if offset.checked_add(newtext.len()) > Some(ct.len()) {
        return Err(CpalError::CiphertextTooShort(offset));
    }

    let mut spliced = plain;
    spliced.splice(offset..offset + newtext.len(), newtext.iter().copied());
    Ok(ctr::ctr(&spliced, key, NONCE)?)
}

    ct: &[u8],

) -> Result<Vec<u8>, CpalError> {
    let keystream = edit(0, &vec![0u8; ct.len()])?;
    if keystream.len() != ct.len() {
        return Err(CpalError::LengthMismatch {
            a: ct.len(),
            b: keystream.len(),
        });
    }

CTR bit-flipping

set4::l002
The problem · official

There are people in the world that believe that CTR resists bit-flipping attacks of the kind to which CBC mode is susceptible. Re-implement the CBC bit-flip exercise to use CTR mode instead of CBC mode. Inject an "admin=true" token.

The idea

CBC's bit-flip (L16) corrupts one ciphertext byte and lets the chained decrypt scramble the next block. CTR has no chain to corrupt: each plaintext byte is just its ciphertext byte XORed with one keystream byte, P[i] = C[i] ^ K[i]. So the move is not to flip a bit but to write one. With the key and counter fixed, the keystream is a fixed function of the two, and one known (P, C) pair recovers it byte-for-byte: K[i] = P[i] ^ C[i]. The attacker already knows the whole plaintext (the public delimiters plus their own input) and already holds the ciphertext. Over the one fully-known 16-byte block they compute K[i] and rewrite C'[i] = K[i] ^ P'[i] so the block decodes to input ++ ";admin=true;". Every byte outside that block stays bit-identical, so the rest of the profile still decodes cleanly and the check door finds the injected token.

Core move

CTR trades the CBC flip for a random access write: one known pair leaks the keystream over a 16-byte window, and that window is the attacker's free variable. Rewrite it to decode to the token, touch nothing else, and the front door's escaping never gets a chance.

The code

The level module is the CTR twin of L16: a fixed, hidden AES-128 key, a fixed public counter, two doors that sandwich input between public delimiters, and the rewrite. The keystream comes from util/ctr.

pub fn forge() -> Vec<u8> {
    let input = "AAAA"; // 4 bytes: the range = input ++ first 12 suffix bytes
    let mut ct = encryption_oracle(input);
    let plain = build_plain(input);

    let mut target: [u8; BLOCK] = [0u8; BLOCK];
    target[..input.len()].copy_from_slice(input.as_bytes());
    target[input.len()..].copy_from_slice(TARGET.as_bytes());

    for (j, _) in target.iter().enumerate() {
        let i = RANGE + j;
        let keystream = plain[i] ^ ct[i]; // K[i], from the one known pair
        ct[i] = keystream ^ target[j]; // C'[i] = K[i] ^ P'[i]
    }
    ct
}
pub fn solve() -> bool {
    is_admin(&forge())
}

The check door decrypts and looks for ";admin=true;".
  • No new CpalError variant: the check door is a bool, and a CTR failure (which CTR, being a stream, never produces) simply reports false. No Result, no padding.
  • solve is the two lines that run the whole attack: forge, then ask the check door. The doctest pins solve() == true.
